# 📅 SPBSTU A.2.17 Schedule Monitor

Сервис мониторинга изменений в расписании аудитории А.2.17 СПбПУ. Автоматически отслеживает изменения и отправляет уведомления в Telegram.

## 🔧 Как это работает

Сервис запускается как Windows-служба и работает в двух режимах:

**Мгновенные проверки** (каждые 10 минут):
1. Запрашивает актуальное расписание через API СПбПУ
2. Сравнивает со снапшотом
3. Если есть изменения — сразу отправляет уведомление в Telegram, обновляет снапшот и сохраняет изменения

**Сводные проверки** (в 10:00 и 17:00):
1. Расписание загружается один раз и используется и для мгновенной, и для сводной проверки
2. Затем сравнивает эталон (`current`) с новым расписанием
3. Отправляет сводку если есть изменения
4. Обновляет эталон и снапшот
5. Проверяет конфликты в расписании; каждый неразрешённый конфликт повторяется в каждой сводке

**Отправка в Telegram:**
- Сначала пробует отправить напрямую (3 попытки)
- Если не вышло — пробует через резервный HTTP-прокси на VPS
- Если и это не удалось — сообщение сохраняется в очередь
- При следующей проверке очередь пытается отправиться повторно, с пометкой о задержке
- Для длинных сообщений в очередь попадают только недоставленные части, поэтому уже отправленные части не дублируются
- После `outage_alert_threshold` последовательных ошибок загрузки приходит одно предупреждение; после восстановления доступа приходит отдельное сообщение

Все рабочие JSON-файлы сохраняются атомарно: сначала данные полностью записываются и синхронизируются во временном файле, затем `os.replace()` заменяет целевой файл. При аварии во время записи предыдущая версия остаётся целой.

## Диагностика

Безопасная проверка всех интеграций запускается из каталога проекта:

```powershell
.\venv\Scripts\python.exe diagnose.py
```

Скрипт проверяет конфигурацию, JSON-файлы, доступность RUZ для каждой аудитории,
Telegram через прокси и напрямую, права чтения Google Calendar и состояние
Windows-службы. Тестовое сообщение в Telegram не отправляется, календари и
рабочие данные не изменяются. Код завершения `1` означает, что найдена хотя бы
одна критическая ошибка; предупреждения возвращают код `0`.

## ⚙️ Конфигурация мониторинга

Рабочие параметры находятся в `schedule_config.json`:

```json
{
    "building_id": 69,
    "rooms": {
        "1948": "Room A.2.17(Stationary)",
        "1949": "Room А.2.17(Mobile)"
    },
    "semester": {
        "start_date": "2026-09-01",
        "end_date": "2027-01-31"
    },
    "check_interval_seconds": 600,
    "summary_times": ["10:00", "17:00"]
}
```

После изменения конфигурации перезапусти Windows-службу. При запуске сервис проверяет типы значений, формат дат `YYYY-MM-DD`, формат времени `HH:MM` и корректность диапазона семестра.

## 📆 Google Calendar

Сервис синхронизирует расписание RUZ с отдельным дополнительным календарём для
каждой аудитории: создаёт новые управляемые события, обновляет изменившиеся и
удаляет отменённые. Затем он читает дополнительный и прод-календарь. Если событие
уже есть в дополнительном календаре, но в прод-календаре нет события с точно
совпадающими датой, временем начала и временем окончания, в Telegram
отправляется список дат с пропусками — без времени и названий предметов.
Прод-календари сервис никогда не изменяет.

Расхождения между RUZ и дополнительным календарём не отправляются в Telegram,
но записываются в лог с уровнем `WARNING`. Запись показывает интервалы, которые
есть только в RUZ (`missing_in_synchronized`) или только в дополнительном
календаре (`extra_in_synchronized`).

1. В Google Cloud создай проект, включи **Google Calendar API** и создай
   **Service Account** с JSON-ключом.
2. Сохрани ключ как `private_config/google_service_account.json`. Каталог
   `private_config` уже добавлен в `.gitignore` и не должен попадать в Git.
3. В дополнительных календарях предоставь service account право на изменение
   событий, а в прод-календарях — право **«Просматривать все сведения о
   мероприятиях»**.
4. Для каждого календаря узнай идентификатор: **Настройки → Интеграция
   календаря → Идентификатор календаря**.
5. Заполни секцию `google_calendar` в `schedule_config.json`:

```json
"google_calendar": {
    "enabled": true,
    "synchronized_calendars": {
        "1948": "synchronized_calendar_for_room_1948@group.calendar.google.com",
        "1949": "synchronized_calendar_for_room_1949@group.calendar.google.com"
    },
    "production_calendars": {
        "1948": "calendar_id_for_room_1948@group.calendar.google.com",
        "1949": "calendar_id_for_room_1949@group.calendar.google.com"
    },
    "credentials_file": "private_config/google_service_account.json",
    "timezone": "Europe/Moscow"
}
```

6. Установи зависимости и перезапусти службу:

```bash
pip install -r requirements.txt
sc stop ScheduleMonitorService
sc start ScheduleMonitorService
```

При первом успешном цикле сервис проверит календарь `1948` только по расписанию
аудитории 1948, а календарь `1949` — только по аудитории 1949. Ошибка чтения
Google Calendar записывается в `logs/schedule_service.log`, но не останавливает
остальные проверки RUZ и Telegram-уведомления.

## ⚙️ Установка

### 1. Клонировать репозиторий
```bash
git clone https://github.com/Kent-PR/SPBSTU-a217-schedule-monitor.git
cd SPBSTU-a217-schedule-monitor
```

### 2. Установить зависимости
```bash
pip install requests pywin32
python Scripts/pywin32_postinstall.py -install
```

### 3. Создать файл с кредами
Создай каталог `private_config`, а в нём файл `tg_credentials.py`:
```python
TG_TOKEN = "твой_токен"
TG_CHAT_ID = "твой_chat_id"
TG_EXTRA_CHAT_IDS = ["chat_id_второго", "chat_id_третьего"]  # необязательно
TG_PROXY = "http://адрес_vps:порт"  # резервный прокси на случай недоступности Telegram
```

### 4. Инициализировать расписание
```python
from main import run_check
run_check(is_summary=True)
```

### 5. Установить и запустить сервис
```bash
python schedule_service.py install
sc start ScheduleMonitorService
```

## 🛠️ Управление сервисом

```bash
sc start ScheduleMonitorService    # запустить
sc stop ScheduleMonitorService     # остановить
sc query ScheduleMonitorService    # статус
python schedule_service.py remove  # удалить сервис
```

## 📦 Зависимости

- `requests` — HTTP-запросы к API и Telegram
- `pywin32` — Windows-сервис

Установка зависимостей приложения:

```bash
pip install -r requirements.txt
```

Установка зависимостей для разработки и запуск тестов:

```bash
pip install -r requirements-dev.txt
python -m pytest
```

Во время тестов файловое логирование автоматически отключается через `SCHEDULE_MONITOR_DISABLE_FILE_LOGGING=1`, поэтому искусственные ошибки pytest не попадают в рабочий `logs/schedule_service.log`.
